## 1. Перечень автоматизируемых сценариев

### Навигация к форме записи
- Переход к форме через кнопку «Записаться» на странице профессии
- Переход к форме через скролл страницы профессии до конца
- Переход на страницу профессии с главной страницы через меню «Каталог курсов»
- Переход на страницу профессии с главной страницы через промо-контент/баннер

### Заполнение формы записи (без отправки)
- Позитивный сценарий: заполнение всех полей валидными данными
- Негативные сценарии по каждому полю: пустое обязательное поле, невалидный формат телефона, невалидный формат email
- Проверка визуальной валидации (подсветка ошибок, всплывающие подсказки) при некорректном вводе
- Проверка состояния кнопки отправки при неполном заполнении формы

## 2. Инструменты

- **Selenide + JUnit 5** — для UI-автоматизации: знакомый стек, короткий и читаемый код, встроенные ожидания (Selenide) снижают количество flaky-тестов на динамическом сайте с анимациями/лендингами
- **Page Object Pattern** — для поддерживаемости кода при частых изменениях вёрстки лендинга (маркетинговые страницы меняются чаще, чем внутренние приложения)
- **Allure** — для наглядного репортинга менеджменту/маркетингу, не связанному с разработкой, со скриншотами шагов
- **GitHub Actions** — для CI, чтобы регрессия проверялась автоматически при каждом изменении тестов

## 3. Необходимые разрешения, данные, доступы

- Официальное разрешение от владельцев продукта/маркетинга на автоматизированное тестирование прод-сайта (или тестового стенда/staging-окружения, если такое существует)
- Доступ к staging/тестовому окружению, идентичному продакшену, чтобы не отправлять реальные заявки в CRM
- Договорённость с отделом продаж/CRM о фильтрации/удалении тестовых заявок, если тестирование всё же идёт на проде
- Тестовые данные: валидные ФИО, телефоны, email, не привязанные к реальным людям
- Доступ к репозиторию/CI для настройки автоматического прогона

## 4. Риски при автоматизации

- **Реальная отправка заявок** — при ошибке в тестовом коде (например, случайный клик по кнопке «Записаться») в CRM попадёт мусорная заявка, что создаёт лишнюю нагрузку на отдел продаж и портит конверсию
- **Изменение вёрстки лендинга** — маркетинговые страницы часто редизайнятся A/B-тестами, из-за чего селекторы могут ломаться чаще, чем на внутренних страницах приложения
- **Отсутствие data-test-id** — на лендинге, в отличие от внутренних сервисов компании, вероятно нет устойчивых атрибутов для тестирования, из-за чего селекторы придётся строить по CSS-классам/тексту, что менее надёжно
- **Динамический контент** — A/B-тесты и персонализация могут показывать разным пользователям разные варианты формы/страницы, усложняя стабильность тестов
- **Нет тестового окружения** — если тестировать приходится на проде, риск отправки реальных заявок возрастает многократно

## 5. Необходимые специалисты

- **QA-инженер автоматизатор** — написание и поддержка тестов
- **Frontend-разработчик** — консультация по структуре страницы, добавление data-test-id атрибутов при необходимости
- **DevOps-инженер** — настройка CI/CD пайплайна для регулярного прогона
- **Менеджер продукта/маркетинга** — согласование разрешений на тестирование прод-окружения, доступ к staging
